# 单个常驻 Deno worker：实现与复测

2026-10-28，Apple M5 / 32 GiB / macOS 26.5.1 / Go 1.27.3。
v8go v0.9.0（V8 11.1）对比 Deno 2.9.8（V8 15.0）。

## 实现结果

最终方案保留 RunCode 接口，默认构建使用常驻 Deno；`-tags v8go` 可显式回退。
进程在首次调用时启动，主程序会在接收流量前预先检查运行时；后续调用共享该
进程，每个请求创建全新 Context。SDK 和规则在本次 Context 中
执行，结果通过带 ID 的换行 JSON 协议返回。

Go 使用互斥锁串行处理，并发调用在锁上等待。排队时间不计入脚本执行超时，
但仍计入调用方的总等待时间。没有承诺严格 FIFO，也没有有界队列或取消接口。
超时后杀死并回收进程，关闭管道，等待旧读写结束；下一个请求重建进程。
JS 普通异常保留 worker；进程退出或协议故障会丢弃 worker，失败请求不会重放。
主程序退出时调用 CloseRuntime 释放子进程。

新增测试验证：

- 16 个并发请求串行完成，总排队时间超过单次执行预算也不会误报超时。
- 每个请求使用独立全局变量和原型；响应不会串到其他请求。
- 超时后的排队请求恢复，使用新 PID，旧进程被回收。
- 正常请求复用 PID；JS 错误不会无谓重启；意外退出与关闭后均可重新启动。
- 启动失败恢复、30 万字节响应、跨管道缓冲区的中文/换行输入输出。
- 原有 7 条规则配置继续匹配 v8go 基线；日期与基础脚本/规则超时测试通过。

Deno JS SDK 测试连续运行 5 次通过；JS SDK 与规则模块竞态检测通过。
v8go 回退构建的相关测试通过。早期测试因 Redis 未启动而未全通过；最终切换
验证使用绑定本机临时端口的 Redis 容器，默认 Deno 的 `go test -race -count=1 ./...`
全部通过。另通过四平台编译、22 项发布工具测试及内置 Deno 的容器健康/规则加载验证。

## 同一基准的耗时对比

每项每个后端三轮，每轮预热 7 次、记录 210 次，共 630 个样本；轮换后端顺序，
顺序运行。旧的每次启动版本使用修改前保留的二进制，当场复测；新 worker 与
v8go 使用同一任务和 RunCode 计时边界。预热排除了常驻进程的一次性启动。

- 最小脚本均值：每次启动 Deno **14.561 ms** → 常驻 **0.194 ms**；
  v8go **0.605 ms**。常驻的 p50 / p95 为 **0.166 / 0.346 ms**。
- 现有规则均值：每次启动 Deno **16.638 ms** → 常驻 **0.227 ms**，
  降低约 **98.6%**；v8go **0.691 ms**。
  常驻的 p50 / p95 为 **0.195 / 0.345 ms**；
  每次启动版本的 p50 / p95 为 **14.632 / 17.578 ms**。
- 日期转换均值：每次启动 Deno **17.678 ms** → 常驻 **0.568 ms**，
  降低约 **96.8%**；v8go **2.477 ms**。
  常驻的 p50 / p95 为 **0.524 / 0.831 ms**。

每次启动版本的规则均值受第一轮较高值影响：三轮为 20.598 / 14.435 /
14.882 ms，保留了全部样本，没有删除异常值。上一份独立测试中该版本均值为
15.076 ms，两次结果均显示进程启动是主要负担。

这里常驻 Deno 的耗时也低于当前 v8go，是“保留运行时、只新建 Context”与
“每次新建/销毁 Isolate”、引擎版本及缓存行为共同作用的结果；不能据此推断
Deno 对所有脚本或整条 RSS 链路都更快。第一次请求、超时后的第一次恢复请求
仍需启动进程；以上是正常热态调用，非冷启动指标。

## 短任务内存

独立进程运行 70 次测量调用加 7 次预热，约每 1 ms 采样进程树 RSS：

- 最小脚本：v8go **14.22 MiB**，每次启动 Deno **38.52 MiB**，常驻 **54.75 MiB**。
- 规则任务：v8go **15.25 MiB**，每次启动 Deno **40.95 MiB**，常驻 **57.58 MiB**。
- 日期任务：v8go **17.66 MiB**，每次启动 Deno **43.89 MiB**，常驻 **75.72 MiB**。

常驻减少了启动开销，也保留了运行时的缓存与堆。短测试峰值不能替代持续运行
后的内存预算，后续持续运行测试观察到更高的驻留平台。

## 持续运行与内存

分别对 Deno worker 和 v8go 顺序运行：循环 7 条规则加 1 次日期转换，运行
180 秒，每次开始间隔至少 5 ms，随后空闲 30 秒。每约 100 ms 采样 Go 与子进程
RSS；不保存逐次延迟数组，避免基准自身的数组增长污染长期内存结果。

Deno 完成 **32,377 次**测量调用，全程仅一个 worker PID，无重启。进程树 RSS：

- 10–40 秒均值 **104.81 MiB**。
- 60–90 秒均值 **105.42 MiB**。
- 120–150 秒均值 **101.95 MiB**。
- 150–179 秒均值 **105.65 MiB**。
- 全程采样峰值 **111.63 MiB**；空闲末段 200–209 秒均值 **66.18 MiB**，
  最后采样为 **65.13 MiB**，其中 Go **11.45 MiB**、Deno **53.67 MiB**。

本次 3 分钟、3 万多次调用未观察到随 Context 数量持续线性增长；空闲阶段也
出现了 RSS 回落。但这不等于数天运行无泄漏，不同规则、输入大小和并发排队
仍可能带来更高峰值。

v8go 对照完成 **32,893 次**调用，进程 RSS 早期均值 **22.12 MiB**、末段均值
**23.52 MiB**、采样峰值 **24.58 MiB**；最后采样 **18.11 MiB**。当前单 worker
混合负载的末段 RSS 约为此 v8go 对照的 **4.5 倍**，需要为速度收益预留内存。

持续运行中的 Deno 平均执行耗时为 **1.011 ms**（不包含节拍 sleep），高于短时
突发基准的规则均值。这是包含混合任务、长期 GC 与调度的另一种负载，不应把
0.227 ms 直接当成持续生产负载的固定延迟。同一持续负载下 v8go 平均执行耗时
为 **1.852 ms**。两次均顺序运行在日常使用机器上，并非独占、固定 CPU 频率的
实验环境；突发基准与持续采样不在同一时段，长期比较应看内存趋势与量级。

本轮保留单个 worker，不增加池大小，也未添加基于请求数的定期重启；所有
Context 生命周期验证及持续运行均针对这一真实配置。

## 使用与重跑

```sh
# 默认构建使用常驻 Deno
CGO_ENABLED=0 go build -o rss-can-deno .

go build -tags v8go -o /tmp/rss-can-bench-v8 ./scripts/bench-jssdk
CGO_ENABLED=0 go build -o /tmp/rss-can-bench-deno ./scripts/bench-jssdk
python3 scripts/bench-jssdk/compare.py \
  --v8 /tmp/rss-can-bench-v8 --deno /tmp/rss-can-bench-deno \
  --output /tmp/rss-can-worker-bench.json

python3 scripts/bench-jssdk/soak.py \
  --binary /tmp/rss-can-bench-deno --label deno-worker \
  --output /tmp/rss-can-deno-soak.json
python3 scripts/bench-jssdk/soak.py \
  --binary /tmp/rss-can-bench-v8 --label v8go \
  --output /tmp/rss-can-v8-soak.json
```

Deno 可通过 RSS_CAN_DENO 指定。compare.py 的 `--deno-once` 可附加一个已保存的
旧版每次启动二进制；当前生产后端不再包含该模式。soak.py 的 RSS 采样需要
macOS 的 libproc；可调整 `--duration`、`--idle`、`--interval`。

RSS 汇总同时计入 Go 和 Deno，共享页可能重复计数，也可能漏掉很短的峰值；
不是独占物理内存。基准未包含 RSS 服务其他模块、Chromium 或 Redis。

原始数据：`2026-10-28-deno-worker.json` 为逐次耗时与短时内存；
`2026-10-28-deno-worker-soak.json` 和 `2026-10-28-v8go-soak.json` 为持续采样。
