# Deno 每次启动进程与 v8go 的本机对比

> 历史报告：当前源码已移除 v8go 后端。下文的 `-tags v8go` 命令仅适用于保留该后端的历史版本；当前 `compare.py --v8` 仅接受预先保存的旧基准二进制。


本报告记录原始每次启动方案；后续常驻实现与复测见 [deno-worker.md](deno-worker.md)。

2026-10-28，Apple M5 / 32 GiB / macOS 26.5.1，Go 1.27.3。
v8go v0.9.0（V8 11.1.277.13）对比 Deno 2.9.8（V8 15.0.245.2）。
使用当前工作区的 Deno 原型；没有修改生产执行器或实现进程池。

## 结论

如果继续采用 Deno，建议下一步验证常驻 worker，并按实际并发决定是否扩成池。
当前每次调用启动进程的成本明显高于规则本身：启动到 ready 加终止回收平均
12.48 ms，约占规则调用总耗时的 83%。这说明复用进程有明确的优化方向；
并不代表常驻模式一定能省掉同样的时间，实际收益仍需实现后测量。

如果规则只在启动或缓存失效时执行，十几毫秒可能可以接受；日期转换却同样
经过 RunCode，逐条转换会放大成本。串行执行 1,000 次当前日期任务，按照
本次均值估算，Deno 为 17.65 秒，v8go 为 2.80 秒，额外约 14.86 秒。
这些数字不包含网络抓取，不能直接当作 RSS 请求整体的性能差距。

## 耗时结果

以下为三轮共 630 次调用的合并分布，单位毫秒；每轮先预热 7 次。

- 最小脚本：v8go 平均 **0.623**，p50 **0.591**，p95 **0.719**；
  Deno 平均 **14.456**，p50 **14.051**，p95 **16.492**。均值约 **23.2 倍**。
- 现有规则配置生成：轮换全部 7 条规则，v8go 平均 **0.710**，p50 **0.679**，
  p95 **0.866**；Deno 平均 **15.076**，p50 **14.616**，p95 **17.363**。
  均值约 **21.2 倍**；每次额外 **14.37 ms**。
- 日期转换：完整加载 Moment 和日期函数，再转换固定日期。v8go 平均
  **2.796**，p50 **2.507**，p95 **3.641**；Deno 平均 **17.653**，
  p50 **17.126**，p95 **18.825**。均值约 **6.3 倍**。
- 单独的 Deno 启动探针：运行相同 runner 和 CLI 参数，等待 ready 后终止并
  回收，不发送 SDK 或规则。平均 **12.476**，p50 **12.174**，p95 **13.423**。

规则任务三轮均值：v8go 为 0.712 / 0.720 / 0.699 ms；
Deno 为 15.601 / 14.689 / 14.939 ms。差距在三轮中稳定存在。
当前规则任务串行吞吐约为 v8go 1,408 次/秒、Deno 66 次/秒。
这只是本机单任务串行边界，不是并发负载或线上容量测试。

“启动成本”包含 Go 创建进程、Deno 初始化、加载 runner 与 node:vm、ready
通信以及终止/回收。它不是纯 OS fork/exec 时间，也不是生产调用内的精确分段追踪。
从总量扣除启动探针，规则约剩 2.60 ms，日期约剩 5.18 ms；只能用于说明
潜在优化空间，不能作为进程池性能预测。

## 内存结果

另开进程测量，每个任务执行 70 次，加 7 次预热。按约 1 ms 间隔采样整棵
进程树的 RSS，同时使用 getrusage 保留各进程峰值数据。时间分布来自未采样
的独立运行，避免将内存监测开销混入主结果。

- 最小脚本：v8go 整棵进程树峰值 **14.30 MiB**；Deno **38.36 MiB**。
- 现有规则：v8go **15.45 MiB**；Deno **41.53 MiB**，约 **2.7 倍**。
- 日期转换：v8go **18.09 MiB**；Deno **44.48 MiB**，约 **2.5 倍**。

Deno 数字同时包含 Go 主进程和正在执行的 Deno 子进程，不能只看 Go 的 RSS
或 Go heap。RSS 求和会重复计算跨进程共享页，也可能漏掉短于采样间隔的峰值；
因此它是驻留集指标，不是独占物理内存。

这些是最小基准程序的峰值，未包含整个 RSS 服务、浏览器或 Redis；也未测量
长期驻留后的稳态增长。常驻进程会让运行时内存保留在空闲时段，多 worker 又会
增加驻留成本，所以不应仅为了省启动时间就按 CPU 核数预开大量进程。

## 下一步建议

先做 **1 个常驻 Deno worker**，保持每次请求新建 JS Context，SDK 与规则只在
本次 Context 内共享。不要复用已被规则修改过的 Context。

Go 超时后杀死并回收该 worker，后续请求重新启动；补充并发排队、超时重启、
请求间隔离与长时间 RSS 测试，再使用相同任务复测。只有串行 worker 出现实际
排队压力时，再扩为有上限的小池。若主要负担来自日期转换，也可先考虑批量
转换，减少跨进程次数。

## 重跑

从仓库根目录执行；Deno 从 PATH 查找，也可以设置 RSS_CAN_DENO。

```sh
go build -tags v8go -o /tmp/rss-can-bench-v8 ./scripts/bench-jssdk
CGO_ENABLED=0 go build -o /tmp/rss-can-bench-deno ./scripts/bench-jssdk
python3 scripts/bench-jssdk/compare.py \
  --v8 /tmp/rss-can-bench-v8 \
  --deno /tmp/rss-can-bench-deno \
  --output /tmp/rss-can-bench-results.json
```

compare.py 在 macOS 使用系统 libproc 采样进程树 RSS；其他系统仅执行延迟测试，
仍保留 getrusage 数据。`--rounds 0` 可只跑 macOS 内存采样。
每种后端预先编译，测量不包含 go build/go run；采用轮换顺序的顺序测试，没有
同时竞争 CPU。操作系统和运行时缓存已预热，不代表重启机器后的首次冷启动。
两者引擎版本不同，这里比较当前可用实现的实际成本，不是对引擎的独立比较。

原始逐次耗时、每轮 getrusage 数据、进程树峰值、环境及合并统计保存在同目录
`2026-10-28-deno-v8go.json`。
